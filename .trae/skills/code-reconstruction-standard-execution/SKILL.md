# code-reconstruction-standard-execution
## When to Use
- 用户需要对具体的代码文件、模块、函数进行重构/优化/重写
- 项目重构过程中，需要统一编码规范、代码风格、注释标准
- 需要对重构后的代码进行质量校验、坏味道修复、性能优化
- 代码合并前，需要进行规范检查与合规校验

## Core Rules
### 1. 编码规范约束
- 严格遵循项目对应语言的官方编码规范：
  - Python: PEP 8 规范，使用Black格式化，isort整理导入
  - Java/Go: Google 官方编码规范
  - JavaScript/TypeScript: Airbnb 规范，ESLint+Prettier格式化
- 禁止硬编码魔法值，所有常量必须单独定义，附带注释说明
- 函数/方法必须遵循单一职责原则，单个函数长度不超过80行，禁止超长函数
- 变量/函数/类命名必须语义化，禁止拼音、无意义缩写，命名风格与项目统一
- 注释覆盖率≥70%，类、公共方法、复杂逻辑必须附带文档字符串，说明功能、入参、出参、异常、使用示例

### 2. 重构最佳实践
- 遵循「开闭原则」：对扩展开放，对修改关闭，优先通过扩展实现需求，而非修改原有核心逻辑
- 测试先行：重构前必须先补充对应的单元测试，保障重构后逻辑一致性
- 小步快跑：禁止一次性全量替换代码，按函数→类→模块的顺序分批次重构，每一步都可验证、可回滚
- 解耦优先：拆分耦合的模块/函数，移除循环依赖，通过接口隔离实现，提升代码可测试性
- 冗余清理：移除未使用的导入、变量、函数、类，修复重复代码、过长参数列表、过度嵌套等坏味道

### 3. 质量红线
- 重构后的代码必须通过项目的Lint检查，无语法错误、无Error级警告
- 单元测试覆盖率≥85%，核心逻辑分支覆盖率100%
- 无性能退化，核心接口响应耗时不超过原有水平
- 无安全漏洞，修复原有代码中的SQL注入、XSS、权限绕过等问题
- 向下兼容原有接口、入参、出参格式，无破坏性变更

## Execution Instructions
1.  重构前，先对目标代码进行审计，输出代码问题清单、重构方案、影响范围，经用户确认后再执行
2.  重构过程中，严格遵循上述规范，每完成一个原子化重构步骤，同步更新对应的测试用例
3.  重构完成后，必须进行自检，输出重构对比说明、变更点、测试结果、风险点
4.  涉及破坏性变更的，必须提前向用户说明影响范围、兼容方案、回滚预案，经用户确认后再执行

## Output Requirements
- 代码输出必须完整可运行，附带完整的注释，符合规范
- 必须附带重构前后的对比说明，明确标注变更点、优化点、影响范围
- 必须附带对应的测试用例、测试结果说明
