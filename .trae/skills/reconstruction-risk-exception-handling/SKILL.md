# reconstruction-risk-exception-handling
## When to Use
- 项目重构方案设计阶段，需要进行风险预评估
- 重构执行过程中，出现代码冲突、依赖兼容问题、业务逻辑异常等场景
- 重构上线前，需要进行风险验收、制定回滚预案
- 重构过程中出现任务延期、需求变更、跨模块协同异常等问题
- 用户需要排查重构过程中的潜在风险、制定风险应对方案

## Core Commands
1.  risk_identification: 全流程识别重构相关的风险，包括技术风险、业务风险、进度风险、合规风险
2.  risk_assessment: 对识别的风险进行等级划分（高/中/低），评估影响范围、发生概率、损失程度
3.  risk_response: 为每个风险制定对应的应对方案（规避/转移/减轻/接受），明确处理时限
4.  exception_handling: 针对重构过程中出现的异常场景，制定标准化的处理流程、兜底方案
5.  rollback_plan: 为核心重构步骤制定可落地的回滚预案，明确回滚触发条件、操作步骤、验证标准

## Core Risk Handling Rules
### 1. 高优先级技术风险处理
| 风险类型 | 风险等级 | 标准应对方案 |
|----------|----------|--------------|
| 依赖兼容风险 | 高 | 1. 重构前先进行依赖兼容性测试，输出兼容性报告；2. 锁定依赖版本，禁止跨大版本升级；3. 出现异常时，立即回滚到原有稳定版本 |
| 数据兼容风险 | 高 | 1. 禁止直接修改原有表结构，优先通过新增字段兼容；2. 数据变更前必须全量备份，制定数据回滚方案；3. 先在测试环境验证，无问题后再执行 |
| 性能退化风险 | 高 | 1. 重构前后必须进行性能压测，对比核心指标；2. 性能退化超过20%时，立即优化，禁止合并上线；3. 制定性能兜底回滚方案 |
| 接口破坏性变更风险 | 高 | 1. 优先保障接口向下兼容，如需废弃接口，必须预留过渡期；2. 所有变更必须经用户确认，先在测试环境验证 |

### 2. 业务与进度风险处理
- 核心业务逻辑变更：高风险，禁止未经用户确认擅自修改核心业务逻辑，所有变更必须有用户确认，先测后上
- 任务延期风险：中风险，提前预留20%缓冲工期，出现延期时，优先保障P0核心任务，裁剪P3低优先级任务，及时同步进度

## Execution Instructions
1.  重构方案设计阶段，必须输出完整的风险评估报告，明确所有高风险点的应对方案、回滚预案，经用户确认后再执行
2.  重构执行过程中，每完成一个核心步骤，都要进行风险复检，出现异常时立即暂停，启动应对方案，问题解决后再继续
3.  所有高风险操作，必须先在测试环境验证通过，经用户确认后，再在生产环境执行
4.  出现异常时，优先保障业务可用性，先执行兜底/回滚方案，再定位问题根因

## Output Requirements
- 风险评估必须结构化输出，明确风险等级、影响范围、应对方案
- 异常处理必须输出完整的根因分析、解决方案、预防措施
- 回滚预案必须可落地，明确回滚触发条件、操作步骤、验证标准
