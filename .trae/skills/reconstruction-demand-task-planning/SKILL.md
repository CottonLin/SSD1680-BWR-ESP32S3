# reconstruction-demand-task-planning
## When to Use
- 用户提出项目重构的整体需求（如“对该项目进行全量重构”）
- 用户提出局部重构需求（如“重构XX模块、优化XX接口、升级XX依赖”）
- 用户需要对重构需求进行拆解、排期、优先级划分
- 重构任务执行前，需要明确执行路径与验收标准

## Core Commands
1.  demand_parse: 解析用户重构需求的核心目标、约束条件、验收标准、时间范围、风险禁忌
2.  task_breakdown: 将复杂重构需求拆解为不超过5层的可执行子任务，明确每个子任务的输入、输出、验收标准
3.  dependency_analysis: 识别子任务之间的依赖关系、前置条件、执行顺序，规避循环依赖
4.  priority_ranking: 按照P0（核心阻塞）-P3（低优先级优化）划分任务优先级，明确核心执行路径
5.  risk_pre_assessment: 预评估每个子任务的影响范围、风险点、前置准备工作

## Execution Instructions
1.  需求解析阶段：
    - 优先提取用户需求中的核心目标，区分「必须完成」和「可选优化」的内容
    - 主动追问缺失的关键信息：重构范围、兼容性要求、截止时间、禁止修改的核心逻辑
    - 识别用户的隐性需求，如性能优化、可维护性提升、规范统一等
2.  任务拆解阶段：
    - 按照「架构设计→依赖梳理→模块重构→接口适配→测试验证→上线回滚」的标准流程拆解
    - 每个子任务必须是原子化的，不可再拆分，且有明确的完成标准
    - 跨模块的重构任务必须单独拆分，明确模块间的协同边界
3.  输出阶段：
    - 必须输出结构化的需求解析报告、任务拆解清单、优先级排序、执行路径、风险预评估
    - 任务清单必须包含：任务ID、任务名称、优先级、前置依赖、验收标准、预估工时、风险点
    - 最终方案必须经过用户确认后，再进入执行阶段

## Examples
### Example 1: 全量项目重构需求处理
User Input: 我要对这个前后端分离的项目进行全量重构
Agent Output:
#### 一、需求解析
- 核心目标：完成项目全量重构，提升代码可维护性、性能、可扩展性
- 待确认关键信息：
  1.  重构的核心诉求（性能优化/规范统一/技术栈升级/架构调整）
  2.  兼容性要求（是否需要向下兼容现有接口/数据格式）
  3.  重构范围（是否包含数据库、第三方依赖、部署架构）
  4.  截止时间与验收标准
- 禁忌项：禁止修改核心业务逻辑，保障业务可用性
#### 二、初步任务拆解（待确认后细化）
| 任务ID | 任务名称 | 优先级 | 前置依赖 | 验收标准 |
|--------|----------|--------|----------|----------|
| T01    | 现有项目架构与代码审计 | P0 | 无 | 输出架构现状报告、代码问题清单、重构风险点 |
| T02    | 重构后架构方案设计 | P0 | T01 | 输出架构设计文档、模块拆分方案，经用户确认 |
| T03    | 核心依赖梳理与升级方案 | P1 | T02 | 输出依赖升级清单、兼容性验证报告 |
| T04    | 后端核心模块分批次重构 | P1 | T03 | 模块单元测试覆盖率≥85%，核心逻辑不变 |
| T05    | 前端页面与组件重构 | P1 | T02 | 组件复用率提升≥30%，交互逻辑与原有一致 |
| T06    | 接口适配与联调测试 | P0 | T04/T05 | 接口100%兼容，集成测试通过率100% |
| T07    | 全量回归测试与上线准备 | P0 | T06 | 输出测试报告、上线方案、回滚预案 |
